# 九类错位检查表

> 错位 1–5：2026-08-28，从「AI 产品投资决策工具」单个案例（N=1）抽象
> 错位 6：2026-08-29，假进展（Round 制案例）
> **错位 7–9：2026-08-29，从本地 10 个真实项目的文件系统实测中抽象（N=10）**
> → 其中错位 9 同时**证伪了错位 1–5 时代的一条断言**，见错位 9 末尾

本文件是 `product-investment-review` 的核心资产。
**「四问框架」（NEED/GAP/AI EDGE/FOUNDER FIT）不稀缺——任何人一下午都能写出一套。稀缺的是这套失败模式库。**

> **维护铁律：每一条必须由独立案例产生。**
> 从单次对话中抽象的模式，在下一次真实案例中被证伪的概率很高——
> 错位 9 就是对本文件自身的一条断言的证伪记录。
> **检查表只能靠独立案例变长，不能靠推理变长。**

## 错位 1 — 框架 vs 信息

### 模型

```
决策质量 = f(信息, 框架, 校准, 后果承担)
```

| 要素 | 稀缺性 | 一般产品提供？ | 可替代性 |
|---|---|---|---|
| 信息（竞品真实数据、付费意愿、市场大小） | **极高** | ❌ 常缺 | 低 |
| 框架（四问 / 检查表 / 流程） | **极低** | ✅ 常是核心卖点 | **极高** |
| 校准（prediction vs outcome） | 高 | ❌ 常排在路线图末尾 | 低 |
| 后果承担 | — | ❌ AI 不承担 | — |

### 自检问题

1. 这个产品的核心输出，是「一个更好的思考方式」还是「用户自己拿不到的信息」？
2. **如果答案是前者** → 用户缺的不是这个。一篇文章、一段 prompt、一份 markdown 就能替代，且更贴合他自己。

### 判定标准

> **如果产品的全部价值可以被「一份写清楚的方法论文文档」替代，错位成立。**

### 现场检验（最有效的一问）

> **「你为什么不直接问 ChatGPT？」**

如果答案只是「我们 prompt 更好」「我们更结构化」——**错位成立**。

## 错位 2 — 否定者 vs 选择者

### 四个付费触发点

| 触发点 | 心理 | 痛感 |
|---|---|---|
| a) 我已经浪费了 3 个月，想知道我为什么会判断错 | 事后 | ✅ 真实 |
| b) 我有 12 个 idea 只能选 1 个 | **选择**（正和） | ✅ 真实 |
| c) 我要向合伙人 / 投资人 / 自己证明这笔投入是理性的 | **解释**（正和） | ✅ 真实 |
| d) 我有 idea，请来否定它 | 事前 | ❌ **几乎不存在** |

### 自检问题

产品瞄准的是哪一个？

### 判定标准

> **如果产品把自己定位成「否定者」，高度怀疑。**
> 正在兴奋于自己 idea 的人，不会主动寻求一个专门否定它的工具。

### 体检悖论（类比）

体检市场的真实客户不是「有健康焦虑的人」，而是：

- 被强制体检的人
- 已经出现症状的人
- 有钱到把健康管理当项目做的人

**主动寻求否定，是一种反人性的理性。它存在，但撑不起一个市场。**

## 错位 3 — 需求错配

### 矩阵

```
                 缺它            不缺它
有痛感      ← 新手但已失败 →    ← 老手/多次失败 →   （缺的是信息）
无痛感      ← 纯新手 →          ← 无所谓 →          （不会付费）
```

### 自检问题

1. 有痛感的人（做坏过项目的），缺的是这个产品给的东西吗？
2. 缺这个东西的人（新手），有痛感吗？

### 判定标准

> **如果「有痛感的不缺它，缺它的没有痛感」，产品落在对角线上。**

典型形态：向已经会做框架的人推销框架。

## 错位 4 — 冷启动悖论

### 自检问题

1. 护城河在路线图第几步？
2. 入口（第一步）有没有护城河？
3. **用户有理由走到护城河那一步吗？**

### 判定标准

> 护城河在最后、入口无护城河、且中间步骤零沉淀 → **死锁**。
> 用户流失 → 沉淀不发生 → 护城河永远到不了。

### 4b 变体（最致命）

**核心价值需要 N 次样本 / M 个月才能显现**（典型：判断准确率、推荐质量、个性化）。

追问：

> **在样本攒够之前，用户凭什么留下来？**

推理链（以「AI 判断可信度」为例）：

```text
产品卖的是「判断可信」
  → 判断可信只在统计意义上成立
  → 单次用户对统计无感（对了觉得是常识，错了觉得是垃圾）
  → 统计需要 20+ 次样本 ≈ 12 个月
  → ∴ 核心价值在前 12 个月既不可证实也不可证伪
```

**两条解法：**

1. **让单次使用就有价值** —— 只能靠**信息**（查到他自己查不到的），不能靠**判断**（他自己也会）
2. **历史回填** —— 不让他慢慢积累，而是第一次就挖出他已经发生的历史：
   `git history / 项目目录 / 死掉的分支 / 旧档案 / 过去的记录`

> **历史回填是冷启动悖论唯一的结构性解。**

## 错位 5 — 输出层 vs 数据层

### 自检问题

1. 产品的输出（报告 / 判断 / 建议）下面，有没有一个独有数据层托底？
2. 如果这个输出层被拿走，用户还剩下什么？

### 判定标准

> **卖一个悬空的输出层 = 把护城河建在最不稀缺的地方。**

### 类比

知识图谱类产品的真正资产是图里的节点和关系，**不是那份诊断报告**。
报告只是数据资产的编辑输出层。先盖输出层后补数据层，是最常见的顺序错误。

## 错位 6 — 假进展（pseudo-progress）

### 定义

引入了**看起来是进展、实则不产生新信息的结构性动作**。

### 三个典型载体

| 载体 | 假在哪 |
|---|---|
| **阶段 / 轮次 / 等级编号** | 「我从 Round 1 到了 Round 2」——中间没有可判定的验证发生，编号本身就成了进展感的来源 |
| **流水线阶段推进** | 01→02→03 走完一遍，每一步都「完成了」，但没有一步被证伪过 |
| **成熟度评分 / 健康度分数** | 分数会涨，因为**投入**在涨——但涨的不是价值的证据，是成本的证据 |

### 自检问题

1. 这里有没有一个动作，**做了就自动产生「前进了」的感觉**，却不要求新证据？
2. 去掉这个编号 / 评分，用户还能知道自己有没有进展吗？
3. **进展的依据是「投入增加了」还是「不确定性减少了」？**

### 判定标准

> **如果某个结构的默认动作是「继续」而不是「重新申请」，它在制造假进展。**

### 与承诺升级的关系

Round 制是 VC 的真实结构，因为 VC 有**分批注入的外部资本 + 沉没成本的信号效应**：
投了 Seed 就有强动机投 A，否则前面的钱打水漂。

独立开发者没有外部资本也没有下一轮投资人，他的资源是**注意力，且不可并行**。
把 Round 制移植过来，等于把「承诺升级」写进产品的默认路径。

> **「批准下一笔投入」要求新证据；「进入下一轮」只要求上一轮别太惨。**

# 附：抗吞噬测试

> **如果这个能力明天被模型原生支持，这个产品还剩什么？**

## 高危区（正被厂商零边际成本填满）

| 能力 | 为什么危险 |
|---|---|
| 写代码 | Cursor / Claude Code / Codex 主场，且有 IDE 工程壁垒 |
| 写 PRD / 文档 | 只是模型的既有能力释放 |
| 竞品 / 市场分析 | 通用 Agent 自己会搜索 |
| 任务拆解 | Agent 已做得很好 |
| **多 agent 编排** | **厂商与框架层第一性战场**（subagents / Agents SDK / LangChain / CrewAI） |

## 安全区

- 用户自己的历史
- 用户的偏误档案
- 用户的结果数据（outcome）
- 本地上下文（模型拿不到）
- 任何需要「承担后果」的判断

## 判定标准

> **产品的价值如果与模型能力成反比，它的生命周期就是模型的一次版本更新。**

### 一个通用规律

**「推理层」和「编排层」都是给弱 agent 打的补丁。**
模型越强，agent 越能自己完成规划、分解、调用子 agent，这两层的独立价值就越薄。

# 附：隐喻反客为主

## 自检问题

1. 产品用的核心隐喻是什么？它原本是**修辞装置**还是**真实行为描述**？
2. 用户真的是那个隐喻里的角色吗？

## 案例

用 VC 语言（Investment Committee / Due Diligence / Portfolio / 漏斗）包装个人开发者的选择问题。

- 漏斗假设用户有 100 个 idea 排队
- 但真实的个人开发者：**不是 idea 太多，是同时能做的只有 1–2 个**
- 他的问题不是「从 100 里选 1」，而是「手上这个要不要继续」
- 绝大部分 idea 诞生 10 分钟内就被自己否定，根本不进系统

漏斗适用于 VC（真的收到 100 份 BP），不适用于个人。

**「投资人视角」原本只是一个帮助自我疏离的修辞装置，后来滑变成了产品的组织架构。**

### 案例 2：Round 0 / 1 / 2 / 3 / 4

用 VC 融资轮次标记个人项目的成熟度。

- 轮次制假设**外部资本分批注入**（Seed → A → B，每轮有新投资人重新做尽调）
- 个人开发者没有外部资本，也没有下一轮投资人
- 轮次制的默认动作是「通过 → 下一轮」，会把项目推向承诺升级
- 而档案里已经记着：**他的项目不是死在验证，是死在第二个功能**

> **轮次制恰恰会让他更顺滑地走到第二个功能。**

解法：把 Round 降级为 **Tranche（一笔投入）**——
花完即回到审查起点重新申请，不自动进入下一阶段。

## 判定标准

> **当产品的功能结构在模仿某个职业的工作流，而用户并不是那个职业的人时——隐喻反客为主。**

### 复发提示

这个病会复发，且每次都穿着新衣服：
漏斗（VC）→ 轮次（VC）→ 尽调清单（VC）→ 投资组合（VC）。
**同一个隐喻反复出现，说明它被当成了本体，而不是工具。**

# 附：递归自检的边界

## 真递归 vs 循环论证

| | 用 X 审 X（伪递归） | 用 X 审 Y（真递归） |
|---|---|---|
| 提出者与审查者 | 同一人、同一上下文 | 同一方法、不同对象 |
| 典型结果 | **必然 INVEST** | 可能 PASS |
| 信息增量 | 零 | 有 |
| 能否暴露偏误 | 不能——内部人偏差满格 | 能 |

## 判定

> **如果一个审查的结果必然是「通过」，它没有产生任何信息。**

用一套方法论审查它自己的升级版，会同时触发三重偏误：
内部人偏差（提出者 = 审查者）、承诺升级（已经投入了，不想判死）、
以及**对自身优雅性的欣赏**（框架越自洽，越容易给自己打高分——自洽不是有效）。

## 实践

想递归检验一个决策方法论，**不要拿它审它自己**，
拿它审**手上沉没成本最大的那个项目**——
那里才有真实的情感阻力，才测得出这个方法是不是只会给出你想听的答案。

## 多 AI 互审能补哪一层（2026-08-29 补）

| 层 | 形态 | 破除什么 | 破不了什么 |
|---|---|---|---|
| 1 | 同一上下文自我审查 | — | **一切**（纯循环论证） |
| 2 | 多 AI 互审，但**共享同一份检查表** | 执行者偏差（谁提出谁审查） | **框架偏差** |
| 3 | 多 AI 互审 + 强制产出**检查表外**的新失败模式 | 执行者偏差 + 部分框架偏差 | 共享的世界知识与训练分布 |

**默认发生的是第 2 层。** 要到第 3 层，必须给角色差异（Bear / 被取代的竞品 /
Premortem / 目标用户），而不是把同一个 prompt 发给三个模型。

# 附：共享框架偏差与检查表陷阱

## 检查表陷阱

> **你只能找到你的检查表里有检查项的那一类错误。**

一份失败模式库如果从 **N=1** 抽象而来，它编码的是**那一个案例的推理路径**。
用它审第 2 个项目时，「全部通过」真正的含义是
**「在这个案例特有的几个维度上没找到问题」**，不是「没有问题」。

### 自检问题

1. 这份检查表的每个条目，来自**几个独立案例**？
2. 有没有一类失败，是这份检查表**结构上不可能发现**的？
   （例：它只检查产品与市场匹配，不检查「用户会不会用第二次」）
3. **上一次有人提出一个检查表外的失败模式，是什么时候？**

### 判定

> **如果一次复审没有扩充检查表，它检验的是结论，不是框架。**
> 而框架才是更需要被检验的那个东西。

## 关于「共识」

多个模型 / 多个复审者给出同一个中间结论，**大概率不是共识，是回归均值**——
LLM 共享训练分布，天然倾向「平衡、全面、合理」的输出。

> **一致性高 = 信息量低。真正有信息量的是分歧点。**

分歧的正确处理不是取平均，是问：
**他们各自看到了什么对方没看到的事实？** —— 那个事实本身就是新检查项。

## 对抗工具：Premortem

> **「假设 12 个月后它已经失败了。写一份复盘：它是怎么死的？」**

| | 预测 | Premortem |
|---|---|---|
| 方向 | 现在 → 未来 | 已发生的失败 → 倒推死因 |
| 受什么污染 | 乐观偏差、规划谬误 | 少得多 |
| 检索路径 | 从「为什么能成」的素材里找 | 从「什么会出问题」的素材里找 |
| 产物可证伪吗 | 常常不可 | **天然可证伪，可直接进 Prediction 那格** |

# 错位 7 — 矩阵幻觉（Matrix Illusion）

> **来源：2026-08-29 项目组合审查，实测 10 个项目目录。**

## 形态

用一份清单 / 矩阵 / 看板管理「产品组合」，但**清单上的状态标签从未与实物核对过**。

本例证据：
一次 10 个项目的组合审查中，2 个标为 **LIVE** 的产品——
实测为 **8 个文件**（其中 3 个是 `.gitkeep` 空占位）和 **10 个文件**（全是微信聊天截图 + 1 份 .docx 想法）。

## 为什么危险

所有资源分配决策都建立在标签上。标签虚标 → **你在一个不存在的产品组合上做组合管理**。

而且标签会自我强化：

```text
写下来是 LIVE
   → 心理上已交付
   → 不再有紧迫感
   → 永远停在 LIVE
```

## 判定标准

> **当一个项目被标为「已完成 / LIVE / 上线」，
> 但找不出它对外产生结果的证据（URL、用户数、DAU、收入、外部反馈任一），
> 该标签为幻觉。**

## 自检问题

1. 这个状态标签，是**事实**还是**愿望**？
2. 能不能给出一个**外部可验证的链接或数字**？给不出 → 标签为幻觉。
3. 上一次核对这个标签是什么时候？

## 衍生规则

> **任何「组合管理」工具的第一功能应该是核对，不是规划。**
> 在清单可信之前，规划只是在虚构上做优化。

# 错位 8 — 元层逃逸（Meta-layer Escape）

> **来源：2026-08-29。这是本 skill 自身最需要被检查的一格。**

## 形态

当执行层变得不确定或痛苦时，退到「决定该执行什么」这一层，
**并把在元层的精雕细琢误认为进展。**

本例证据：
- 最后一个真实项目被触碰：2026-08-14
- 审查日：2026-08-29 → **15 天零项目活动**
- 这 15 天内最重的认知投入：**本 skill 自身，迭代 v1 → v8**
- 而本 skill 的自我定义是：「帮助开发者决定下一笔资源投在哪里」

> **一个「决定资源投在哪里」的工具，在它被造出来的那两周里，
> 资源实际上投在了它自己身上，而所有其他项目停摆。**

## 它不同于「循环论证」

循环论证是**逻辑**问题（用 X 审 X）。
元层逃逸是**行为**问题——不需要 X 自己证明自己，只需要观察**资源流向**。

> **这也是本 skill 能被合法地用于观察自身的唯一方式：
> 不用它的结论，用它的使用数据。**

## 为什么极难被发现

元层的工作**看起来完全像进展**——产出物在变厚、框架在变自洽、每轮迭代都有新洞察。

它具备进展的一切表象，**只缺一样东西：外部结果**。

## 判定标准

> **当你在一个「让人做得更好」的东西上投入的时间，
> 超过了你「实际在做」的时间，你就在元层。**

更锋利的一版：

> **如果这个工具永远不会被用满 3 次，它这几周的精致迭代就等于零。**

## 自检问题

1. 过去 14 天，我在「做事」上花了多少小时？在「决定做什么」上花了多少小时？
2. 如果这个工具从此不再改进一版，我明天会少做成什么？答不出 → 元层。
3. 上一次产生**外部结果**（有人用了 / 有数字变化 / 有外部反馈）是什么时候？

## 硬约束（适用于本 skill 自身）

> **若本 skill 被迭代到第 10 版，但被审查的项目一个都没有实际被推动，
> 判定元层逃逸成立，本方法论下调 🔴，强制停用。**

# 错位 9 — 双峰死亡分布（Bimodal Death）

> **来源：2026-08-29。同时它是对 v1 断言的一次证伪。**

## 形态

项目不是死在一个中间位置，而是聚集在**两端**：
一端从未开始（停在想法），一端投入巨大但停在交付前（停在资产）。

## 本例证据

v1 断言（纯推理，无数据）：「你的项目不是死在验证，是死在第二个功能。」

实测证伪：

```text
投入（文件数）
  ↑
78k│ ● 项目A          ← 峰 A：投入巨大，走得很远，主动降级
33k│   ● 项目B         ← 峰 A：文档 > 代码，分析 > 产品
10k│     ● 项目C
 7k│       ● 项目D      ← 唯一真 LIVE
   │
   │                    ← 中间是空的
   │
 64│         ● 项目E
 15│          ● 项目F
 10│           ● 项目G   ← 峰 B：只有想法和素材，从未开始
  8│            ● 项目H
  0│             ● 项目I
   └────────────────────────────→
```

> **没有项目死在第二个功能，因为没有项目走到过第二个功能还没死的。**

## 两个峰是两种病，需要相反的药

| 峰 | 症状 | 真实病根 | 需要的药 |
|---|---|---|---|
| **峰 B**（从未开始） | 想法、素材、截图、占位目录 | 启动成本 > 心理收益 | **降低启动门槛；或承认它只是想法，删掉** |
| **峰 A**（停在交付前） | 海量资产、极少代码 | **收集本身已提供足够多巴胺**，交付反而剥夺它 | **强制在收集前定义交付物** |

## 峰 A 的病根（单独说）

一个项目：约 7.8 万文件 / 22 个代码文件。
另一个项目：344 文档 / 266 代码。

> **收集即奖励。**
> 当「再爬一批数据」比「把它交给一个用户」更令人满足时，
> 项目就永远停在资产态——**而且当事人会真诚地认为自己在推进。**

## 判定标准

> **若一个项目的输入型产出（爬取的资料、整理的文档、做的图）
> 与输出型产出（可交付的代码、面向外部的结果）之比 > 10:1，
> 它已经进入资产态，不是产品。**

## 对本 skill 自身的教训

> **从 N=1 抽象出的模式，会在 N=10 时被证伪。**
> v1 的断言若照着设计产品，会做出一个「防止过度开发」的工具——
> 而真实需求是「防止不开始」和「防止不交付」，**方向相反**。

# 错位 10 — 资产态加速（Asset-state Acceleration）

> **来源：2026-10-15 Prediction 重跑。47 天实测。**

## 形态

AI 让「收集与整理」的边际成本趋近于零，而「交付与分发」的成本不变。

**结果不是产出变多，是收集/交付比急剧恶化——
项目更快地进入资产态，然后停在那里。**

## 本例证据

| 指标 | 2026-08-29 | 2026-10-15 | 变化 |
|---|---|---|---|
| 项目目录数 | — | — | **+140%** |
| 文件总量 | — | — | **+194%** |
| 最大单项目文件数 | 约 7.8 万 | **约 9.0 万** | 45 天造出一个更大的 |
| 面向外部的分发动作 | — | **文件系统无证据** | **0** |


> **十个并行的内容形态，零个交付出口。峰 A 的教科书形态，规模创历史新高。**

## 它比「收集即奖励」更危险

| | 收集即奖励（错位 9） | 资产态加速（错位 10） |
|---|---|---|
| 机制 | **心理**：收集本身给多巴胺 | **经济**：收集成本趋零 |
| 能否靠自觉抵抗 | 能（意识到即可） | **不能** |
| 为什么 | 是欲望问题 | **是不经济问题** |

> **即使你完全理性、完全清楚自己在逃避，
> AI 也会让逃避变得如此便宜，以至于不逃避显得不经济。**

## 判定标准

> **若一个项目在 AI 辅助下 30 天内文件数增长 >10,000，
> 但同期对外分发动作 = 0，
> 则它不是在成长，是在以最快速度沉淀为资产。**

## 它对 Founder Fit 判定的修正（重要）

08-29 判定「整理与结构化」是唯一能走完闭环的能力，是**真实资产**。

45 天后必须修正：

> **「整理与结构化」在 AI 时代正在快速贬值——因为 AI 自己就能整理。**
> **它恰恰是最先被 AI 吞噬的那一格。**
>
> → 任何把 Founder Fit 建立在「我擅长整理/结构化/写框架」上的项目，
> 都要重新做抗吞噬测试。

# 附：Prediction 设计原则

> **来源：2026-10-15 重跑时发现本文件自身的缺陷。**

## 缺陷

第 3 条 Ledger 的 P2 设计为「是否出现 ≥2 个真实目录（文件数 ≥20）」，判定**命中**。
但这个命中**毫无校准价值**——建目录是用户一直在做的事，
**无论审查是否生效，它都会发生。**

> **一个 Prediction 如果检验的是「用户本来就会做的事」，
> 它测的不是方法论的效果，是时间。**

## 原则

> **Prediction 必须检验「若无本方法论则不会发生的动作」，
> 而不是「随时间自然发生的动作」。**

| ❌ 会自然发生（无效） | ✅ 不会自然发生（有效） |
|---|---|
| 目录数增长 | 主动**删除**一个项目 |
| 文件数增长 | 主动**降级**一个 LIVE 标签 |
| 新建项目 | 主动**停止**一个正在兴奋的项目 |
| skill 迭代 | 主动**对外发出**一次 |
| 文档变厚 | 主动**填写** Ledger 的 Outcome |

## 自检问题

写 Prediction 时问自己：

> **如果这个方法论完全无效，这件事还会发生吗？**
> 会 → 这条 Prediction 测的是时间，重写。

## 附：逾期本身是数据

> 三条 Prediction 检验日 09-28 / 09-30，实际重跑 10-15，**逾期 17 天**。
>
> **一个决策系统连自己的检验日都没触发——
> 这不是疏漏，这是它在优先级里的真实位置。**

# 附：最后一击清单

如果以上检查都没找到致命伤，用这三条做终检：

1. **最强反例**：从用户自己的历史里找一次「该早点停手」的决策，问——**这类审查能不能救他？**
   若不能，说明产品拦得住平庸的错误，拦不住结构性的错误。这划出了产品的能力边界。
2. **删除测试**：删掉某个功能，价值还成立吗？用于区分 Core Value 与 Feature。
3. **一句话测试**：用户能自然说出「我用它是为了 ______」吗？说不出来 = 定位没想清楚。

# 错位 10 — 被杀 idea 的复活（2026-08-30 新增，来自 AI Product OS 案例）

## 定义

一个已被否决的 idea，**换一个更完整的名字、配一份更细的架构、分期更清楚**之后重新出现，
**且未携带任何新证据**。

## 现场证据

```text
2026-08-28  v5 提出「AI Product Orchestrator / Product OS」
            → 被否：⑤ Agent Orchestration 是异类，编排层是给弱 agent 打的补丁
2026-08-30  同一机制以「AI Product OS / Project Bot」回归
            → 22 节任务书、V0.1/0.2/0.3/1.0 四期、6 类 Specialist Agent
            → 新增内容：架构更细、分期更完整
            → 新增证据：**无**
```

## 判定标准

> **「更完整」不是新证据。完整性是伪装得最好的一种原地踏步——
> 它能让提案者真诚地觉得「这次不一样」，因为这次的文档确实厚得多。**

判定方法：**比对历史 Kill Line 记录**，看新提案的**核心机制**是否已被否决过。
只要核心机制（不是名字、不是架构细节）相同 → 视为复活，
**默认沿用原 verdict**，除非能指出「上次否决所依据的那条假设，现在被什么证据推翻了」。

## 复活的三个识别特征

| 特征 | 表现 |
|---|---|
| 换名不换机制 | Product Orchestrator → Product OS，机制仍是「给每个项目配 AI 管家」 |
| 用规模掩盖缺口 | 上次被指出的缺口（分发 / 编排是雷区）这次没补，但文档从 5 节涨到 22 节 |
| 分期自带承诺 | V0.1→V1.0 四期编号，等于预先许诺「这次会走完」（见错位 6） |

> **对付复活的唯一有效动作，是把上次的否决理由原样贴回来，问一句：
> 「上次否决所依据的那条，现在哪一条变了？」**

# 错位 11 — 用不存在的样本做验证设计（2026-08-30 新增）

## 定义

验证方案（dogfood / 试点 / 测试集）里列出的样本，**本身查无实物**。

## 现场证据

任务书第 20 节原文：「不要寻找虚拟项目做测试，直接使用已有项目作为 Dogfood」，列 8 个。
逐条核对文件系统：

```text
项目 A      ✅ 39,474 files
项目 C      ✅    298 files
项目 H      ⚠️     40 files（8-29 已判虚标 LIVE）
项目 D      ⚠️     10 files（8-29 已判虚标 LIVE）
项目 E      ❌ 查无
项目 F      ❌ 查无
项目 G      ❌ 记忆路径不存在
某内容项目   ❌ 查无
→ 8 个里 3 个查无实物，2 个是空壳。真可 dogfood 的 2 个。
```

## 判定标准

> **一份验证方案如果连样本存不存在都没核对过，它验证的不是产品，是提案者的想象。**

## 强制动作

验证方案列出样本后，**逐个 `ls` 核对**，输出文件数。
任一查无 → 该条从样本列表剔除，并追问：

> **「你列这个名字的时候，是在回忆一个项目，还是在回忆一个想法？」**

## 与错位 7（矩阵幻觉）的关系

错位 7 是**状态标签**未与实物核对（标 LIVE 实则空壳）；
错位 11 是**验证样本**未与实物核对（说要用它做 dogfood 实则不存在）。
**同一个病根在更高一层的复发 —— 名字在清单里就算存在。**

> 这个病根的一句话总结：
> **对他来说，「写下来」这个动作本身就产生了存在感。清单是他的本体，实物是他的影子。**
